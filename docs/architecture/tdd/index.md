# 测试驱动开发（TDD）

测试驱动开发（Test-Driven Development）是一种**先写测试、再写实现**的开发方式。它的核心信条是：测试不是开发的附属品，而是**设计工具**——在写任何实现代码之前，先写一个会失败的测试，让测试告诉你"功能应该长什么样"。

本文先讲 TDD 解决什么问题，再讲红绿重构循环与测试策略，最后用 xUnit 对一个订单域做完整的 TDD 演练。示例代码位于仓库 `src/TDD`，是 DDD 文档中订单域的"测试驱动版"。

## 解决什么问题

传统开发"先写实现、后补测试"会积累三个问题：

1. **测试永远补不齐**：功能上线后测试就失去动力，覆盖率随迭代不断下降，回归全靠人肉。
2. **设计被实现绑架**：直接写实现时，脑子里全是"怎么存、怎么调"，而不是"行为应该是什么"，容易过度设计或设计不足。
3. **改代码如履薄冰**：没有测试网兜底，重构不敢做，坏味道只能忍着，代码越来越烂。

TDD 把顺序颠倒过来：**先写测试，实现是被测试"逼"出来的**。这个颠倒带来两个转变：

- 写测试时被迫先想清楚**行为契约**（输入、输出、异常），设计从"怎么实现"转向"应该做什么"。
- 每个功能都有测试兜底，重构变得安全，"坏了马上知道"。

## 核心循环：红-绿-重构

TDD 是一个极短的三步循环，像交通灯一样严格：

```text
🔴 红：写一个会失败的测试（先跑，确认它失败）
🟢 绿：用最简单的代码让测试通过（不追求优雅）
🔧 重构：消除重复与坏味道（测试保证行为不变）
```

### 第一步：红（Red）

写一个**针对新行为的测试**，运行它，确认失败。失败是好事——它证明测试真的在检验目标行为，而不是"永远通过的空壳"。

### 第二步：绿（Green）

用**最简单粗暴**的方式让测试通过。可以写死返回值、可以复制粘贴，怎么快怎么来。此时不优化，因为测试网刚织好一角，过早优化只会让实现和测试纠缠不清。

### 第三步：重构（Refactor）

测试全绿后，代码是安全的——可以放心地提取方法、消除重复、改进命名。重构完再跑一遍测试确认行为没变。**先保证正确，再追求优雅。**

为什么必须是这个顺序？因为测试先行强制你**先定义"完成"的标准**，实现只是达标的过程；而重构放在绿之后，是因为没有测试网的重构是走钢丝。

## 测试策略

TDD 循环解决"怎么测"，测试策略解决"测什么、测到什么程度"。

### 测试金字塔

测试按成本与数量呈金字塔分布：

| 层级 | 数量 | 速度 | 覆盖对象 |
| :--- | :--- | :--- | :--- |
| 单元测试 | 最多 | 毫秒级 | 单个类/方法的行为，不依赖外部系统 |
| 集成测试 | 适中 | 秒级 | 模块协作、数据库、外部服务 |
| 端到端测试 | 最少 | 分钟级 | 完整用户旅程 |

TDD 主要发生在**单元测试层**：它最快、最稳定，能精确指出问题所在。金字塔越往上，测试越慢越脆，数量应越少。

### 测试命名

测试名应描述**行为**而非步骤。中文行为描述是清晰的选择：

```csharp
[Fact]
public void 单件商品_总额等于单价乘数量() { ... }

[Fact]
public void 已支付订单_不能再添加商品() { ... }
```

一眼就能看出被测行为与预期结果，失败时不用翻代码猜意图。

### 什么该测、什么不该测

- **该测**：业务规则、边界条件（数量为 0、负数、重复操作）、状态流转、算法。
- **不该测**：框架行为（EF Core 怎么生成 SQL）、第三方库、纯 getter/setter、UI 布局。
- **测试替身**：被测对象依赖数据库、网络时，用替身（Stub/Fake/Mock）替换外部依赖，让测试只关注本单元的逻辑。测试项目引入 `NSubstitute`、`Moq` 等库即可。

## 实战演练：xUnit 对订单域做 TDD

现在用 xUnit 对一个订单域做完整的 TDD。目标功能（需求列表）：

1. 单件商品订单，总额 = 单价 × 数量。
2. 多件商品订单，总额 = 各行小计之和。
3. 商品数量必须大于 0，否则拒绝。
4. 满 3 件打 9 折；否则满 500 元减 50 元。
5. 已支付订单不能再修改；重复支付必须被拒绝。

工程结构（`src/TDD`）：

```text
src/TDD
├── OrderDomain/            # 被测类库（领域实现）
│   ├── Order.cs            # 订单聚合根
│   ├── OrderItem.cs        # 订单行
│   ├── OrderStatus.cs      # 状态枚举
│   ├── Money.cs            # 金额值对象
│   └── DiscountRules.cs    # 折扣规则
└── OrderDomain.Tests/      # xUnit 测试项目
    ├── OrderTests.cs
    └── DiscountRulesTests.cs
```

### 第一轮：红——先写失败的测试

需求 1 是"单件商品总额 = 单价 × 数量"。**先写测试**，测试里声明的 API 就是我们对订单聚合的设计契约：

```csharp
// OrderTests.cs（红阶段）
[Fact]
public void 单件商品_总额等于单价乘数量()
{
    var order = new Order();
    order.AddItem("机械键盘", new Money(899m), 2);

    Assert.Equal(new Money(1798m), order.TotalAmount);
}
```

运行 `dotnet test`，测试失败——因为 `TotalAmount` 还没实现（返回 0）：

```text
[xUnit.net] OrderDomain.Tests.RedDemoTests.单件商品_总额等于单价乘数量 [FAIL]
失败!  - 失败:     1，通过:     0，已跳过:     0，总计:     1
```

红色确认：测试确实在检验目标行为。

### 第一轮：绿——用最简单实现通过

现在实现 `TotalAmount`，一行代码：

```csharp
public Money TotalAmount => _items.Aggregate(Money.Zero(), (sum, item) => sum + item.Subtotal);
```

再次运行，测试通过，进入绿色。

### 第一轮：重构——提炼小计

`Subtotal` 是订单行的职责，且"单价 × 数量"的算法会被多处使用，把它收进 `OrderItem`：

```csharp
public class OrderItem
{
    public Money UnitPrice { get; }
    public int Quantity { get; }

    /// <summary>小计 = 单价 × 数量</summary>
    public Money Subtotal => UnitPrice * Quantity;
}
```

重构后重新运行测试，全绿，行为未变。

### 第二轮：参数化测试覆盖需求 2 与 3

需求 2"多件商品总额之和"直接补一个测试即可。需求 3"数量必须为正"用 `[Theory]` 参数化一次覆盖 0 与负数两个边界：

```csharp
[Theory]
[InlineData(0)]
[InlineData(-1)]
public void 商品数量必须大于零(int quantity)
{
    var order = new Order();

    Assert.Throws<ArgumentException>(() => order.AddItem("机械键盘", new Money(899m), quantity));
}
```

这次测试先跑：失败（`AddItem` 尚未校验数量）→ 在 `AddItem` 加一行 `if (quantity <= 0) throw ...` → 全绿。同样的节奏，需求 5（状态流转约束）也照此办理。

### 第三轮：折扣规则的数据驱动测试

需求 4 折扣规则有多个分支，独立成 `DiscountRules` 类方便单独测试。用 `[Theory]` 把规则的两个分支与优先级全部铺开：

```csharp
[Theory]
[InlineData(200, 2, 0)]     // 不足 3 件且不满 500 元：无折扣
[InlineData(1000, 3, 100)]  // 满 3 件：打 9 折，优惠 10%
[InlineData(600, 1, 50)]    // 不满 3 件但满 500 元：减 50
[InlineData(600, 3, 60)]    // 同时满足：9 折优先
public void 折扣规则_按条件计算优惠(decimal total, int itemCount, decimal expected)
{
    var discount = DiscountRules.Calculate(new Money(total), itemCount);

    Assert.Equal(new Money(expected), discount);
}
```

对应的实现（先跑失败，再补上分支逻辑）：

```csharp
public static Money Calculate(Money total, int itemCount)
{
    // 规则一：满 3 件打 9 折，优惠金额为总额的 10%
    if (itemCount >= 3)
        return total * 0.1m;

    // 规则二：未满 3 件但满 500 元，直减 50 元
    if (total.Amount >= 500)
        return new Money(50m, total.Currency);

    return Money.Zero(total.Currency);
}
```

### 全量运行

所有需求完成后的最终状态（`dotnet test`）：

```text
测试运行成功！
测试总数: 11
     通过: 11
```

11 个测试覆盖了订单总额、数量校验、状态流转、折扣规则四个行为面。每一次需求推进都经历了"红 → 绿 → 重构"，最终实现与测试一一对应——**测试清单就是需求清单**。

## 典型应用场景

- **规则密集的业务逻辑**：金额计算、状态机、校验规则，TDD 让每条规则都有测试背书。
- **修复 bug**：先写一个复现 bug 的失败测试，再修复实现，测试转绿后永久留在测试套件里，防止回归。
- **设计探索**：接口或算法还没想清楚时，测试先行能快速验证行为契约，避免过度设计。
- **重构与升级**：测试网兜底，让重构、框架升级可以放心进行。
- **不适合的场景**：一次性脚本、探索性原型、纯展示页面，TDD 的投入产出比很低。

## 总结

- **红-绿-重构**：先写失败测试定义行为契约，用最简单实现转绿，再在测试保护下重构。
- **测试是设计工具**：TDD 的价值不只是"有测试"，更是让设计从行为出发、让代码可验证。
- **金字塔决定投入**：单元测试为主，集成与端到端测试为辅，按成本分配数量。
- **与 DDD 互补**：测试驱动出"刚刚够用"的设计，DDD 提供完整建模语言；两者结合，领域规则既有模型承载、又有测试护航。
