前面讲的四次挥手，是双方都正常存活时的"和平分手"。但现实中连接断开更多是"意外"的：对方崩溃、断电、拔网线……这些情况没有任何报文能通知，TCP 是怎么发现的？又该如何处理？下面分几种场景来看。

## 空闲时拔网线：靠探测发现

双方都没有数据发送时，如果一方拔掉了网线（或断电），对端是察觉不到的——没有数据在传输，就没有超时触发，TCP 会一直认为连接还活着；甚至拔线的一方自己，也要等到下次尝试发送数据时，才会发现网络已经不通了。发现问题的途径主要有两种：

- **TCP KeepAlive**：内核自带的保活机制，连接空闲一段时间后（常见实现为 2 小时）主动发送探测报文，对端不响应就重试，多次无响应后判定连接失效并关闭。
- **应用层心跳**：聊天、游戏、物联网等应用往往不依赖系统机制，而是自己定期发送心跳数据，短时间内收不到对方响应，就认为连接断了，主动重连。

这也就是"基础概念"一篇中说的空闲超时——连接长时间没有数据交互时，靠主动探测来确认对方是否还活着。

## 传输中拔网线：靠重传失败发现

如果拔网线时正在传输数据，情况就更直接了：发送端发出数据后一直在等 ACK，而拔线意味着 ACK 永远等不到了，于是触发重传。注意重传不是试一两次就放弃的，而是超时时间逐次翻倍（指数退避），最多重试约 15 次；全部失败后，TCP 才判定连接失效，向应用层报错（比如 Socket 异常、超时）。

至于那些已经发出去的数据，自然就"消失"在网络里了。TCP 不会无限重试，最终会放弃并把结果告诉应用层，由应用层决定怎么办——比如稍后重发，或者直接重连。

## send 返回成功，就代表发送成功了吗？

不是。调用 Send/Write 时，返回值只代表数据已经成功复制到内核的发送缓冲区，**绝不代表对方收到了**——连接断没断，内核协议栈同样不知道，它只有通过"发出数据、等待回应"才能事后发现。所以网线拔了之后，Send 照样会返回成功，数据静静地躺在缓冲区里发不出去。这不是 bug，而是 TCP 的固有特性：发送方永远无法立刻知道连接已经断了。

那 Send 会在发送前主动探测一下连接状态吗？也不会。内核不会在每次发送前发探测报文确认连接活着，它只是把数据放进缓冲区；只有当连接已经被判定失效时（比如之前收到过 RST、或重传超限），后续的 Send 才会立即抛出异常。正常情况下，"探测"都是被动的，完整过程如下：

```text
send() 返回成功          ← 数据已进入发送缓冲区（此刻没人知道连接已断）
  │
  ▼ 内核开始发送并等待 ACK
  ├─ 收到 ACK        → 正常继续传输
  ├─ 超时            → 按指数退避重传（1s → 2s → 4s → … → 120s 封顶）
  │                   约 15 次失败、持续十几分钟到半小时后，判定连接失效
  └─ 收到 RST        → 立即判定连接失效，无需等待超时
  │
  ▼ 连接被标记为失效
  │
  ▼ 下一次 Send / Receive → 立即抛出 SocketException
```

连接被判定失效后，C# 层会发生什么？

- 正在阻塞的 Send/Receive 会被唤醒并抛出 SocketException，常见错误码有两个：10054（ConnectionReset，"连接被对方强制关闭"）和 10060（TimedOut，"对方在超时时间内没有响应"）。
- 之后的 Send/Receive 因为连接已标记为失效，会立即抛出同样的异常。
- 但如果应用层之后再也不碰这个 socket，就什么都不会发生——程序会一直以为连接是好的。

这里还有一个常见误区：`Socket.Connected` 属性并不可靠，它只反映"最近一次 I/O 操作时"的连接状态——拔线后不做任何操作，它依然是 true。

所以生产环境的通用做法是：**应用层自己定期发送心跳数据（几秒到几十秒一次），配合 ReceiveTimeout 设置接收超时，捕获 SocketException 后触发重连**。不要把断线检测寄托在内核默认的重传超时上——默认参数下，从断线到被发现可能长达半小时。

## 断开还有哪些情况？如何重连？

除了拔网线，连接断开还有几种常见情况：

- **一方崩溃或断电**：对端收不到 FIN，只能靠重传超时或 KeepAlive/心跳发现。
- **RST 复位**：程序异常退出、收到不认识的数据包、连接被对端重置时，TCP 会直接回复 RST 报文立即断开，不经过四次挥手。
- **服务端主动断开**：超时策略、停机维护等（"连接的建立与断开"一篇讲过）。

至于重连：TCP 本身没有自动重连机制——连接断开就是断开了，重连是应用层的责任：捕获到连接异常后，重新发起 Connect，也就是再走一次三次握手。常用的策略是**指数退避**：第一次失败等 1 秒、第二次等 2 秒、第三次等 4 秒……避免在服务端还没恢复时疯狂重试，反而加重它的负担。
