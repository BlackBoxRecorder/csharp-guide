TCP 最核心、也最容易被误解的一个特性是：**它的编号是给"字节"编的，而不是给"包"编的；每个报文段里装多少字节，是不固定的。** 这决定了 TCP 对应用层呈现为一个无消息边界的字节流。

## 序列号是"字节编号"，不是"包编号"

在 TCP 的世界里，根本没有"数据包"这个概念，它把数据看作是**源源不断的字节流**（就像水管里的水流）：

- 当你调用 `send(buffer, 2000)` 时，TCP 会把这 2000 个字节看作一个连续的流。
- TCP 会给这 2000 个字节中的每一个字节，都分配一个唯一的、递增的序号。
- 比如初始序列号是 1001，那么这 2000 个字节的序号就是 `1001, 1002, 1003 ... 直到 3000`。

当 TCP 要把这些数据打包发送时（这个包在 TCP 里叫**报文段 Segment**），包头里会写一个 `Sequence Number`，但它指的是**"这个包里包含的第一个字节的序号"**。比如一个包里装了 100 个字节，第一个字节的序号是 1001，那么这个包的序列号就写 `1001`。接收端看到这个包，就知道这是字节流中从 1001 开始的 100 个字节。

## 一个报文段里装多少字节？不固定

报文段的大小取决于几个"关卡"：

**关卡一：MSS（最大报文段大小）—— 硬限制**

在三次握手建立连接时，双方会协商一个 MSS。通常 MSS = MTU（以太网 1500 字节）- IP 头（20 字节）- TCP 头（20 字节）= **1460 字节**。这意味着一个 TCP 报文段里最多只能装 1460 字节的数据；应用层数据超过 MSS，TCP 就会拆成多个报文段发送。

**关卡二：滑动窗口（流量控制）—— 接收端说了算**

接收端会通过窗口字段告诉发送端"我现在最多还能接收 N 个字节"。如果接收端窗口只剩 500 字节的空间，发送端就会把数据切成 500 字节左右的报文段发过去。

**关卡三：拥塞窗口（网络拥堵控制）—— 网络说了算**

发送端会根据网络的拥堵情况，自己算出一个"拥塞窗口"。如果网络不好，它会故意把报文段发小一点、发慢一点。

**关卡四：应用层写入的时机（Nagle 算法）**

如果你连续调用两次 `send`，每次发 50 字节，TCP 可能会等一等，把这两个 50 字节拼成一个 100 字节的报文段再发（这就是 Nagle 算法，为了减少小包浪费网络资源）。当然，你也可以禁用它（`NoDelay = true`）。

### 举个例子

假设你在 C# 里调用了一次 `socket.Send(myBuffer)`，其中 `myBuffer` 有 **3000 字节**：

1. 给这 3000 字节编号：`Seq 1001` 到 `Seq 4000`。
2. 检查 MSS，假设是 1460。
3. TCP 把它们切成大约 3 个报文段（实际大小可能因选项略有不同）：
   - 报文段 1：字节 `1001` 到 `2460`（共 1460 字节），包头写 `Seq=1001, Length=1460`。
   - 报文段 2：字节 `2461` 到 `3920`（共 1460 字节），包头写 `Seq=2461, Length=1460`。
   - 报文段 3：字节 `3921` 到 `4000`（共 80 字节），包头写 `Seq=3921, Length=80`。

接收端看到 `Seq=1001` 就知道这是字节流的开头，看到 `Seq=2461` 就知道这是接着 `1001+1460` 之后的数据。如果报文段 2 丢了，接收端只会回复"我已经收到 1001 到 2460，下次请从 2461 开始发"，发送端只需重传包含 2461 到 3920 的那一段。

### 总结

| 问题 | 答案 |
| :--- | :--- |
| 每个包都有编号吗？ | 有，但编号是"第一个字节的序号"。 |
| 每个包含多少字节？ | 不固定，通常在几十到 1460 字节之间。 |
| 是固定大小吗？ | 不是，取决于 MSS、接收端窗口、网络拥堵、应用层写入大小。 |
| 序列号是连续的吗？ | 是的，基于字节流绝对连续。比如第一个包含 100 字节，下一个包的序列号就是第一个包的序列号 + 100。 |

## 传输层面与应用层面：边界完全不同

在网络传输的底层，数据确实是一个个**报文段**发送的；但在你写 C# 代码的**应用层**视角，接收端并不是按你发送时的"报文"边界来接收的。

- **网络传输层面（内核和协议栈的视角）—— 是报文段**：发送端内核把 `send` 的数据按 MSS 切成一段一段，每段加上 TCP 头交给 IP 层；接收端内核从网卡收到后，检查序列号、按顺序排列，把数据拷贝到接收缓冲区。这一层是有边界的（靠序列号）。
- **应用层视角（你写的 C# 代码）—— 没有"报文"的概念**：当你调用 `socket.Receive(buffer)` 时，你拿到的不是一个个和发送端 `send` 一一对应的报文。**TCP 对应用层提供的是字节流服务，它不保护消息边界。**

### 粘包：发送端发两次，接收端可能一次收完

```csharp
// 发送端
socket.Send(Encoding.UTF8.GetBytes("Hello"));
socket.Send(Encoding.UTF8.GetBytes("World"));

// 接收端
byte[] buffer = new byte[1024];
int len = socket.Receive(buffer);
// len 可能是 10，buffer 里是 "HelloWorld"
```

### 拆包：发送端发一次，接收端可能分两次收

```csharp
// 发送端
socket.Send(Encoding.UTF8.GetBytes("This is a long message...")); // 假设有 2000 字节

// 接收端
byte[] buffer = new byte[1024];
int len1 = socket.Receive(buffer); // 可能只收到 1024 字节
int len2 = socket.Receive(buffer); // 再收剩下的 976 字节
```

为什么会这样？因为 `Receive(buffer)` 的意思是：**"请从接收缓冲区里，最多拷贝 buffer.Length 个字节给我。有多少就给多少，哪怕只有 1 个字节也可以返回。"** 它完全不知道发送端是怎么 `send` 的，也不知道一个"完整的业务消息"有多长。

## 如何定义消息边界

既然 TCP 不保证消息边界，那么**定义边界就是应用层自己的责任**。常见做法有三种：

1. **长度前缀法（最常用、最推荐）**：发送端先发 4 个字节表示数据长度，再发真实数据；接收端先读 4 个字节拿到长度 N，然后循环读取，直到凑齐 N 个字节，这才是一个完整的消息。
2. **分隔符法**：每条消息末尾加一个特殊标记，比如 `\r\n` 或 `\0`；接收端一直读，读到分隔符就认为一条消息结束。
3. **固定长度法**：规定每条消息必须正好 512 字节，不够就补零；接收端每次只读 512 字节。

### 总结

| 层面 | 发送单位 | 接收单位 | 是否有边界 |
| :--- | :--- | :--- | :--- |
| 网络传输层（TCP 内核） | TCP 报文段 | TCP 报文段 | 有（靠序列号） |
| 应用层（C# 代码） | 你调 `Send` 的数据块 | 你调 `Receive` 拿到的字节流 | 无（完全不保证一一对应） |

所以在编程层面，你必须忘记"报文段"，只把它当作一个**永不出错、按顺序到达的字节水管**，然后自己在上面设计协议来拆包。很多新手用 TCP 会遇到"粘包"问题，其实就是没理解这个字节流本质。
