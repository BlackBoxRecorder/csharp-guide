TCP 是可靠的二进制流式传输，能确保数据完整、按正确的顺序到达目的地。它是如何保证可靠性的呢？

从应用层的视角看，比如我们在 C# 中调用 `Socket.Send` 发送一段数据，数据会先进入内核的发送缓冲区，然后由操作系统负责拆包、编号，并把数据正确发送到目的地。

可靠性的核心是"编号 + 确认"：

- 每个数据包都带有一个编号，接收端收到数据后会回复 ACK（确认信号），告诉发送端"这个编号之前的数据我已经收到了"。
- 发送端据此就能知道哪些包已成功送达：某个包迟迟没有被确认时，只需重传缺失的那一个，而不必把之后的数据全部重发。
- 传输过程中出现网络抖动、某个包丢失时，TCP 会自动重传；但重传并非无限进行，同一个包多次重试仍不成功时，TCP 就判定这条连接已经不可用，主动将其断开。

## 乱序的数据如何重组

这里有一个容易误解的细节：发送端确实按顺序发送数据，但网络并不保证包按顺序到达，接收端收到的包可能是乱序的。不过这并不影响最终结果——接收端不会急着把乱序的数据交给应用层，而是先暂存在接收缓冲区中，等编号连续的包全部到齐、按序排好之后，再交给应用层。

比如下面的场景：

1. 发送端依次发送编号 1、2、3 的数据包。
2. 包 2 在传输途中丢失，接收端只收到了包 1 和包 3。
3. 发送端迟迟没有收到包 2 的确认信号，于是重传包 2。
4. 接收端先收到包 3，后收到重传的包 2，数据以乱序到达。
5. 接收端把乱序的包暂存在接收缓冲区，等 1、2、3 全部到齐后按编号排好顺序，再交给应用层。

## 累积确认与快速重传

上面这个例子讲的是接收端如何把乱序的数据重组回来。那反过来看，接收端面对缺包时，确认信号是怎么发的呢？比如发送端发出了编号 1、2、3、4、5 的数据包，接收端只收到了 1、2、3、5（4 丢了）：

- 1、2、3 是连续的，立即交付给应用层；5 是乱序的，暂存在缓冲区里等待 4。
- 接收端回复的 ACK 只确认连续的部分——确认到 3，也就是告诉发送端"我期待下一个是 4"。乱序的 5 即使已经收到，也不会被确认，这就是**累积确认**。
- 因为每次收到乱序的 5，接收端都会重复回复"确认到 3"的 ACK，当发送端连续收到 3 个这样的重复 ACK 时，就会立即重传 4（**快速重传**），而不必干等重传超时。

这里还有一个容易误解的点：如果 4 一直补不上，谁来判定连接出了问题？答案是**发送端，而不是接收端**——接收端是被动方，缺什么就等什么，不会主动判死。负责补救的是发送端：它发现 4 迟迟未被确认就重传，重传一直失败（约 15 次）后，发送端才判定连接失效并向自己的应用层报错。至于接收端，想要感知连接断了，只能靠收到 RST 报文、应用层设置的接收超时（ReceiveTimeout），或者心跳检测。

可见，即使数据包在网络中丢失或乱序，靠着"编号 + 确认 + 重传 + 缓冲区排序"，应用层最终拿到的始终是一份完整、有序的数据流。

## 接收端什么时候把数据交给应用层

规则是：**只要缓冲区里存在从期望编号开始的一段连续数据，就会立即交付，连续几个就交付几个，并不需要凑满多少个**。比如已收到 1、2、4 时，1、2 是连续的，可以马上交付；4 前面缺了 3，只能先留在缓冲区，等 3 到达、连成一片后再一并下发。

那应用层收到的数据岂不是零散的小块，效率不高？确实可能——这正是 TCP 作为字节流协议的特性：它只保证交付的字节连续、有序，但并不保证"一次交付一条完整的数据"。应用层每次能读到多少，取决于发送方发来了多少、接收缓冲区里攒了多少，可能只有几个字节，也可能一次几千字节。所以编写网络程序时，应用层不能假设"一次读取就是一条完整消息"，通常需要自己定义消息边界（比如长度前缀或分隔符），把读到的数据先累积到自己的缓冲区里，凑齐一条消息再处理。具体做法见"序列号与字节流"一篇。

## 数据是如何被"取"走的

那从接收缓冲区读取数据的频率是多少？是操作系统定时把数据取出来交给应用层吗？

不是。内核只负责把收到的数据放进接收缓冲区，数据并不会自动"推送"给应用层——而是应用层主动调用 Receive/Read 来"取"：调用时缓冲区里有数据就立即返回（有多少给多少），没有数据就阻塞或异步等待，等新数据到达后再返回。所以读取的频率和时机完全由应用层代码决定，并不存在固定的时间间隔。

那读取太频繁，每次读到的数据就少；读取不够频繁，延迟又比较大，有参数可以调节吗？

这个权衡确实存在，但它没有直接对应的系统参数——因为"多久读一次"本来就是应用层自己的策略：想要低延迟，就勤快一点、多调用几次读取；想要减少系统调用开销，就等数据攒到一定量再一次性处理。与缓冲区相关的可调参数主要有两个：接收缓冲区大小（SO_RCVBUF，决定内核最多帮你攒多少数据）和发送端的 Nagle 算法（TCP_NODELAY，决定小数据包是否合并后发送）。不过对大多数程序来说，保持默认值即可，真正影响体验的，还是应用层的读取策略。
