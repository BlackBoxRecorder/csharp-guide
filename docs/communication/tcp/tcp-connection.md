TCP 使用三次握手建立连接，四次挥手断开连接。

## 三次握手：建立连接

为什么需要 3 次握手？

客户端主动连接服务端时，交互流程如下：

1. 客户端向服务端发送 SYN 报文，请求建立连接（进入 SYN_SENT 状态）。
2. 服务端收到后，回复 SYN + ACK 报文，既确认收到客户端的 SYN，也表示同意建立连接（进入 SYN_RCVD 状态）。
3. 客户端收到 SYN + ACK 后，回复 ACK 报文确认。服务端收到这个 ACK 后，连接建立，双方进入 ESTABLISHED 状态，开始正常传输数据。

注意两点：第 2 步服务端回复的是 SYN + ACK（同步标志 + 确认标志），而不是单独的 ACK；三次握手一共只有 3 次报文交互，第 3 步完成后连接即建立。

为什么不能只握手 2 次？

- 三次握手让双方都能确认"自己的发送能力和对方的接收能力"正常：第 1 次后服务端确认客户端发送正常；第 2 次后客户端确认双方收发正常；第 3 次后服务端确认客户端接收正常。若只有 2 次，服务端无法确认客户端是否收到了自己的 SYN + ACK，也就无法确认客户端的接收能力。
- 防止已失效的连接请求造成资源浪费。若客户端发送的旧 SYN 报文在网络中滞留后才到达服务端，服务端回复 SYN + ACK 后便会误以为连接已建立并占用资源；三次握手时客户端不会回复 ACK，服务端就能发现并放弃这个无效连接。
- 双方在握手过程中同步初始序列号，为后续的可靠传输做准备。

## 四次挥手：断开连接

为什么需要 4 次挥手？

TCP 是全双工协议，两个方向的数据独立传输，因此每个方向都需要单独关闭。以客户端主动断开为例，流程如下：

1. 客户端发送 FIN 报文，表示自己的数据已传完，请求断开连接（进入 FIN_WAIT_1 状态）。
2. 服务端收到后回复 ACK，确认收到断开请求（进入 CLOSE_WAIT 状态）。此时服务端可能还有数据要发送，连接进入半关闭状态。
3. 服务端把剩余数据全部传完后，发送 FIN 报文，表示自己的数据也已传完（进入 LAST_ACK 状态）。
4. 客户端收到服务端的 FIN 后，回复 ACK 确认。服务端收到这个 ACK 后关闭连接；客户端则进入 TIME_WAIT 状态，等待一段时间后彻底释放连接。

第 2 步与第 3 步不能合并成一次：服务端收到 FIN 后必须立刻回复 ACK，而它自己的 FIN 要等剩余数据全部传完才能发出，两者之间可能存在较长间隔，所以断开需要 4 次报文交互。

主动断开的一方不一定是客户端：服务端同样可以主动发起断开，例如服务端关闭或重启、检测到连接空闲超时、发现异常数据等。此时流程完全对称，只需把上文中的客户端与服务端角色互换即可，对应的状态转换也相同（主动方经历 FIN_WAIT → TIME_WAIT，被动方经历 CLOSE_WAIT → LAST_ACK）。实际使用中客户端先断开只是常见习惯，并非协议限制。
