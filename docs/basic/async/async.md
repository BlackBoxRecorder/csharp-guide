# 什么是异步

写 C# 的你一定用过 `async/await`，但你真的理解异步吗？

为什么 `Task.Run(() => File.ReadAllText(path))` 不算真正的异步？

异步和多线程、并行到底有什么区别？（详见 [异步、多线程与并行](/basic/async/async-task-parallel)）

本系列文章带你从原理层面搞懂异步编程。

## 异步的定义

**异步是一种「等待期间不占用线程」的编程模型。** 它解决的核心问题是：当程序需要等一个慢操作（网络请求、磁盘读写、数据库查询）时，如何让等的时间不被浪费。

一句话总结：**异步解决「等」，并行解决「算」。**

## async/await 的底层原理

`async/await` 在编译期被改写成**状态机**。配合操作系统底层的 **IOCP（Windows）/ epoll（Linux）**，整个过程分三步：

```
① 发起  → 线程跑几微秒，向内核注册"数据好了通知我"，然后线程离开
② 等待  → 【没有任何线程被占用】硬件 DMA 拷贝数据，CPU 不参与
③ 完成  → 内核通知，线程池派一个线程跑后续代码几微秒
```

**核心在第②步：等待期间零线程占用。** 这就是异步能省线程的全部秘密。

所以线程占用从「全程 50ms」压缩到「首尾各几微秒」，一个线程就能轮着服务上千个请求。

## 真异步 vs 假异步

理解了原理，就能分辨什么是真异步、什么是假异步。

### 判据只有一个

**等待期间，有没有线程被占着。** `async` 关键字和 `Task` 返回值都不是证据——它们只是语法糖，真正的异步在操作系统那一层。

### 假异步长什么样

最常见的假异步就是用 `Task.Run` 包装同步方法：

```csharp
// ❌ 假异步：Task.Run 只是"换个地方干活"
Task.Run(() => File.ReadAllText(path))

// ✅ 真异步：等待期间不占线程
await File.ReadAllTextAsync(path)
```

`Task.Run` 只做了一件事：把代码"换个线程执行"。`File.ReadAllText` 内部该阻塞还是会阻塞，只是阻塞的位置从你的线程换到了线程池线程——**把垃圾从左口袋挪到右口袋，垃圾没消失。**

### 时序图对比

假设 3 个并发请求，每个磁盘 I/O 耗时 50ms：

**真异步（`await File.ReadAllTextAsync`）：**

```
时间轴  0ms                    50ms  51ms
请求1   ─发起IO─╮                    ╰─收尾─✓
请求2   ─发起IO─┤   没有线程被占用    ├─收尾─✓
请求3   ─发起IO─╯                    ╰─收尾─✓
线程池   [忙3ms] ····· 空闲,可以服务别的请求 ····· [忙3ms]
```

**假异步（`Task.Run(() => File.ReadAllText())`）：**

```
时间轴  0ms                    50ms  51ms
请求1   ─线程A ══════ 阻塞等磁盘 ══════ ─收尾─✓
请求2   ─线程B ══════ 阻塞等磁盘 ══════ ─收尾─✓
请求3   ─线程C ══════ 阻塞等磁盘 ══════ ─收尾─✓
线程池   [════════ 3个线程全程被钉死 ════════]
```

**I/O 越慢、并发越高，差距越致命。** 50ms 的 I/O，1000 并发时：真异步峰值只要十几个线程，假异步要 1000 个。

## 为什么假异步会要命

### 线程是昂贵的

| 成本项 | 说明 |
|---|---|
| 栈空间 | 每个线程预留 1MB 虚拟内存 |
| 上下文切换 | 会冲刷 L1/L2 缓存，隐藏成本巨大 |
| GC | 线程越多，GC 停顿越久 |

### 线程池饥饿

线程池不是无限扩张的。初始线程数约等于 CPU 核心数，不够时通过"爬山算法"**慢慢注入**新线程，速率大约每 0.5~1 秒才加 1 个。

于是假异步在高并发下的灾难现场：

```
1000 个请求涌入
  → 线程池只有 8 个线程（8 核机）
  → 8 个立刻被阻塞在磁盘 I/O 上
  → 剩下 992 个请求排队，线程注入速率 ~1个/秒
  → 请求延迟从 50ms 飙升到 100+ 秒
  → 客户端超时，上游重试，请求翻倍 → 雪崩
```

**注意症状有多诡异：CPU 使用率可能只有 5%，机器"看起来很闲"，但所有请求都在超时。** 这就是典型的**线程池饥饿（thread pool starvation）**，生产环境最难排查的故障之一。

### 在 ASP.NET Core 上尤其致命

ASP.NET Core 的请求处理本身就跑在线程池线程上：

```csharp
// ❌ 灾难：一次调用吃掉两个线程
app.MapGet("/data", async (string path) =>
{
    var text = await Task.Run(() => File.ReadAllText(path));
    return text;
});
```

请求线程被 `await` 释放了（好事），但另一个线程被阻塞（坏事），**净消耗仍然是 1 个线程，而且白白多了一次线程切换的开销**。相比直接同步调用，它反而**更慢**，却给了你"我已经异步了"的错觉。

更糟的常见变体是同步阻塞：

```csharp
// ❌❌ 双重暴击：当前线程直接死锁等待
var text = Task.Run(() => File.ReadAllText(path)).Result; // 或 .Wait()
```

这里当前请求线程被 `.Result` 阻塞，同时又占了一个线程池线程去干活——**消耗 2 个线程**，而且在有 `SynchronizationContext` 的环境（如经典 ASP.NET、WPF）还会直接**死锁**。

## 一眼分辨真假异步

| 检查项 | 真异步 | 假异步 |
|---|---|---|
| 方法名 | 以 `Async` 结尾，返回 `Task`/`ValueTask` | 返回裸类型或 `void` |
| 内部实现 | 用了 IOCP / epoll / IOCompletionCallback | 最终调用同步阻塞 API |
| 反编译看 | 底层 `TaskCompletionSource` + 完成时回调 | 直接返回值，没有完成通知 |

**最实用的经验法则：如果 API 有 `XxxAsync` 版本，永远优先用它。**

另外，**`Task.Delay` 是异步的，`Thread.Sleep` 不是**——前者注册一个定时器后立刻释放线程，后者死等。用 `.Result`/`.Wait()` 去等待任何 `Task`，都等于把异步又变回同步阻塞。

## Task.Run 的正确使用场景

别把 `Task.Run` 当成反派，用对了是神器。**判据：里面跑的是“算”（CPU）还是“等”（I/O）。**

- **✅ 该用**：CPU 密集型任务，需要让调用方不被卡住（UI 场景、Web 场景）
- **✅ 该用**：被迫调用只有同步 API 的遗留库（无奈但合理的妥协）
- **❌ 不该用**：包一个本身有异步版本的操作（如 `File.ReadAllText`、`httpClient.Send`）

详细使用场景和代码示例请参考 [异步、多线程与并行](/basic/async/async-task-parallel)。

## Linux 上的一个细节

上面说的"真异步完全不占线程"，对**网络和 Windows 上的文件 I/O** 是准确的。但在 Linux 上要打个折扣：

- Linux 的 `epoll` 对**普通文件**基本无效（文件描述符总是"就绪"），所以 .NET 在 Unix 上是用**线程池的 I/O 线程**来模拟文件异步——请求被排到 I/O 线程池，由某个线程完成 `pread`
- 这意味着 `File.ReadAllTextAsync` 在 Linux 上**确实会占用线程**，只是占的是 I/O 线程池，而非工作线程池

但即便如此，它依然远好于 `Task.Run` 包同步调用：因为 I/O 线程池和工作线程池是分开管理的，**阻塞 I/O 线程不会导致请求处理的工作线程饥饿**，雪崩风险被隔离了。

**结论不变：用 `XxxAsync`，永远优于 `Task.Run(() => Xxx())`。**

## 总结

| | 用什么 | 等待/计算时占线程吗 | 提速来源 |
|---|---|---|---|
| **I/O 密集** | `async/await` + `XxxAsync` | 等待期**不占** | 省线程 → 提高并发 |
| **CPU 密集** | `Task.Run` / `Parallel` | 占满一个核（必须） | 多核并行 |

**判断异步真假只看一件事：等待期间有没有线程被占着。** `Task.Run` 只是"换个地方干活"，不会把"等"变成"不等"。`async` 关键字和 `Task` 返回值都不是证据——它们只是语法糖，真正的异步在操作系统那一层。
