服务端要支撑大量并发连接，首先要破除一个直觉：很多人以为"一个连接就得占一个线程"，那是阻塞 IO 时代的思路。现代高并发服务器（Kestrel、Nginx、Redis）的答案是：一条 TCP 连接是极轻的资源，一台普通服务器扛几万、几十万连接并不稀奇。

## 为什么连接是"轻"资源？

- 一条连接只在两端各对应一个 socket 数据结构，由四元组（源 IP、源端口、目标 IP、目标端口）唯一标识；网络中间的设备不保存连接状态，按包转发即可。
- 连接空闲时，内核只需保留少量状态（序号、窗口、定时器），几乎不消耗 CPU。
- 连接主要占用的是内存：每个连接的内核结构加上收发缓冲区，大约十几 KB。一百万连接大概需要 10~20 GB 内存——只要内存够，连接就扛得住。

对比"一连接一线程"的思路就明白了：一个线程默认栈就有 8 MB，一万个线程需要 80 GB 内存，再加上线程调度的开销，服务器早就垮了。所以高并发的关键不是"开更多线程"，而是"用少量线程服务海量连接"——这正是 IO 模型要解决的问题。

## 单机能支持多少个并发连接？

理论上限非常夸张：服务端只监听一个端口，靠四元组区分连接，最多可以有 (2^32 个客户端 IP) × (2^16 个客户端端口) ≈ 281 万亿条。当然这是纯数学上限，现实中主要受三样东西限制：

- **文件描述符（fd）上限**：每个 socket 都占用一个 fd，而进程默认只能打开 1024 个（ulimit -n 的限制），必须调大。
- **内存**：如前所述，每个连接十几 KB，百万连接需要 10~20 GB。
- **客户端端口**：客户端发起连接用的是临时端口，默认范围只有 2.8 万个左右，所以单个客户端能发起的连接数有限；服务端不受此限制。

实际经验：普通配置的服务器稳定支撑几万到几十万连接；百万级（C10M）需要调优内核参数并精心设计应用。

## 高并发的关键：IO 模型

有了海量连接，如何高效地读写它们？这就是 IO 模型的问题。Linux 上的演进大致如下：

- **阻塞 IO**：read 一直等到有数据才返回。实现最简单，但一个线程同时只能服务一个连接——一连接一线程，扛不住高并发。
- **非阻塞 IO + 轮询**：read 立即返回，没数据就返回"暂不可读"。但应用层要不停轮询所有连接，CPU 全浪费在空转上。
- **IO 多路复用（select / poll / epoll）**：用一个线程同时监视成千上万个连接，哪个有数据就处理哪个。这是现代高并发服务器的基石：
  - select：有 1024 个 fd 的数量限制，每次调用都要把全部 fd 从头扫到尾，效率低。
  - poll：突破了数量限制，但仍要遍历所有 fd，连接越多开销越大。
  - epoll：事件驱动，内核只把"就绪"的连接告诉应用，复杂度 O(1)，是 Linux 高并发的标准答案。
- **异步 IO（io_uring）**：读写由内核完成后通知应用，连"等待"都不需要，是新一代高性能方案。

对 .NET 开发者来说，这些底层细节大多被封装了：.NET 的异步 IO（async/await、SocketAsyncEventArgs）在 Linux 上正是基于 epoll 实现的，Kestrel 之所以能支撑百万级并发，底层靠的也是这套机制。

## 如何调整 Linux 参数？

服务端要支撑高并发，需要调整两组限制。

第一组是文件描述符上限。fd 限制其实分三层，任何一层都会卡住你：

- **软限制**：`ulimit -n` 查看，默认 1024，是进程实际生效的限制。
- **硬限制**：`ulimit -Hn` 查看，是软限制的天花板。普通用户只能把软限制调到硬限制为止；要超过硬限制，必须由 root 来改——root 设置软限制时会自动把硬限制一并提高。
- **系统级上限**：`fs.file-max` 限制整个系统所有进程合计能打开的 fd 总数；另外还有一个容易忽略的 `nr_open`，它是单个进程的绝对上限（默认 1048576），就算硬限制设得更大也无效，想超过它得先调大 `/proc/sys/fs/nr_open`。

临时调整用 `ulimit -n 1000000`（仅当前 shell 会话生效）；持久化有两种方式：写入 `/etc/security/limits.conf`（`* soft nofile 1000000`、`* hard nofile 1000000`），或 systemd 服务的 .service 文件中设置 `LimitNOFILE=1000000`。改完后可用 `ulimit -n` 或 `cat /proc/self/limits` 验证实际生效的值。

第二组是内核网络参数，写入 `/etc/sysctl.conf` 后执行 `sysctl -p` 生效：

| 参数 | 作用 |
|------|------|
| net.core.somaxconn | 监听队列（accept 队列）上限，新内核默认 4096，高并发下建议调大 |
| net.ipv4.tcp_max_syn_backlog | 半连接（SYN 队列）上限，防止 SYN 洪水 |
| net.ipv4.ip_local_port_range | 客户端临时端口范围，默认 32768~60999，需要时可扩大 |
| net.ipv4.tcp_tw_reuse | 允许复用 TIME_WAIT 状态的连接（需配合 tcp_timestamps） |
| net.ipv4.tcp_max_tw_buckets | TIME_WAIT 连接数量上限，超出后会被尽快回收 |
| net.ipv4.tcp_keepalive_time | KeepAlive 探测前的空闲时间，默认 7200 秒，可调短以加快发现死连接 |
| net.ipv4.tcp_fin_timeout | 主动关闭方停留在 FIN_WAIT_2 的等待时间，默认 60 秒，可调短 |

一个常见的配置示例：

```bash
# /etc/sysctl.conf
fs.file-max = 1000000
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.ip_local_port_range = 1024 65535
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_max_tw_buckets = 50000
net.ipv4.tcp_keepalive_time = 120
net.ipv4.tcp_fin_timeout = 15
```

注意参数并非越大越好：调大 somaxconn 意味着更多连接排队等待 accept，应用要能及时接受；调短 keepalive_time 会加快空闲连接的淘汰，但也会增加探测报文的开销。实际部署时建议结合压测逐步调整。
