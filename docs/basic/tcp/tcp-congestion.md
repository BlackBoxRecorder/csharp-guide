可靠性解决的是"数据能否完整到达"，拥塞控制回答的则是另一个问题：**数据能发多快？**

## 拥塞与拥塞窗口

链路的带宽是有限的。发送端若不管不顾，一口气把大量数据（比如一个大文件）全部塞进网络，就可能超过链路的承受能力，导致中间设备缓冲区爆满、大量丢包，传输反而更慢——这就是拥塞。好比高速公路的车流超过容量，所有车堵在一起，谁都快不了。

TCP 的应对方式是：发送端维护一个"拥塞窗口"，用它限制同时发出去但还没收到确认的数据量。窗口小，发送就慢；窗口大，发送就快。难的是怎么确定这个窗口的大小——TCP 靠"试探"：

1. 连接刚开始时，拥塞窗口从一个很小的值出发，成倍增长（**慢启动**），快速探测链路的容量。
2. 增长到一定阈值后，改为线性增长（**拥塞避免**），放慢试探的脚步。
3. 一旦出现丢包，TCP 就认为网络拥塞了，把窗口大幅缩小（常见做法是减半），先降速缓一缓，再重新增长。

如此周而复始，发送速度就像"踩油门 → 发现堵车 → 松油门 → 再慢慢加油"，自动找到链路当前能承受的最大速率。

需要说明的是：拥塞控制针对的是"网络"这个中间环节；而接收端处理速度的限制，属于**流量控制**的范畴——接收端通过窗口字段告诉发送端自己还能收多少，前文"缓冲区"一节讲的背压机制正是它。两者共同决定发送端实际能发多快。

## 流量控制：窗口字段如何让发送端慢下来

接收端并不需要发送特殊的"窗口报文"——窗口信息就藏在每个 TCP 报文头部的"窗口大小"字段里。这个字段有 16 位，接收端每次回复 ACK（或发送数据段）时，都会把它填成"当前接收缓冲区还剩多少空间"：

```text
┌──────────────┬──────────────┐
│  源端口(16)  │  目的端口(16) │
├──────────────┴──────────────┤
│         序号 (32)            │
├─────────────────────────────┤
│         确认号 (32)          │
├──────┬───┬────┬─────────────┤
│头长度 │保留│标志│ 窗口大小(16) │
├──────┴───┴────┴─────────────┤
│    校验和(16) │ 紧急指针(16)  │
└─────────────────────────────┘
```

接收端"喊慢"的完整流程是这样的：

1. 应用层从接收缓冲区读走数据，腾出空间，剩余空间变大，窗口值也跟着变大。
2. 应用层读得慢、数据堆积，剩余空间变小，窗口值随之变小。
3. 接收端回复 ACK 时把变小的窗口值带上，发送端看到就明白"对方快满了"。
4. 发送端实际能发多少，取决于两个窗口的较小值：min(拥塞窗口, 接收窗口)。接收窗口变小，在途数据就减少，发送自然慢下来。
5. 缓冲区完全满时，窗口字段填 0，发送端完全停发——这就是**零窗口**。

发送端停发后也不会干等，它会定期发送一个 1 字节的"窗口探测"报文去试探；接收端收到后，会回复一个带最新窗口值的 ACK。一旦应用层又读走了数据、窗口重新打开，发送端就恢复发送。

还有两个值得了解的细节：窗口字段只有 16 位，最多只能通告 65535 字节，对高速网络不够用，所以双方在握手时会协商"窗口缩放"选项来扩大窗口（最多 256 倍）；另外，接收端不会专门发空报文来更新窗口，而是在回复 ACK 或发送数据时"捎带"上最新窗口值，省掉一次多余的报文交互。
